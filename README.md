

# Unigen

**写工作指南，得到 Agent。**

Unigen 让 AI 按你的方式干活。你用自然语言写一份工作指南，Unigen 把它编译成一个能执行的 Agent 系统。单轮问答、多步骤长链条任务都覆盖。指南写得细还是粗，由你按模型能力定。

界面是图形化的：配置工具、编排子 Agent、写指南正文。全程不碰 Markdown、YAML、front-matter 语法。

> 业务讲清楚一次，剩下的交给 AI。

三句话读懂 Unigen：

1. **AI 不懂你的业务，除非你讲给它听**：模型带着它学来的知识工作，并不知道你专属的工作方法。你写的是"这件事在你这里该怎么做"。
2. **零代码**：问答、长链条任务都覆盖，不写一行代码。
3. **过程写多少，模型就照多少走**：模型强的地方指南写粗，模型弱的地方指南写细。同一套底座，靠指南这一份文件适配从前沿大模型到本地小模型。

---

## 一个比喻：你雇苏东坡做电商

先记住这个画面，后面所有道理都从它长出来。

你雇苏东坡来做电商。苏东坡聪明，读过万卷书，会推理——这是他的本事。但他活在宋代，没碰过电脑、后台、SKU、退货率。而且有两件事你改变不了：

- **他工作时，你改不了他脑子里的东西。** 你不能趁他点鼠标时，往他脑中补一条"现代人网购先看评价"的常识。他的知识在他上班前就定型了。
- **他怎么想，你看不见。** 他给你结论，给不了你推导。你没法盯着他的脑回路纠错。

你唯一能做的，是**上班前给他写一份工作指南**。这份指南和给现代员工写的完全不同：

- 给现代员工写"登录后台改价"，他懂。
- 给苏东坡写这句，他卡在"登录"两个字上。你得把"登录"拆开，用他懂的东西讲清楚每一步。

苏东坡就是大模型：**自带知识和推理；推理期你调不动它的知识，也看不见它的推理。** 你能做的只有一件事——针对你的任务，把过程写成指南，编译成 Agent。指南里的每个词、每一步，要对齐模型"见过的世界"，不能假设它懂你脑子里没说出口的业务常识。

这就是 Unigen 在做的事：**把你专属的工作办法，写成工作指南，Unigen会将其编译为Agent，让AI按照你的工作方法干活。**

## Unigen 解决什么问题

想让 AI 接管一段重复工作，今天通常只有两条路，都不顺手：

- **代码框架（LangChain / LlamaIndex）**：要写 Python。精力耗在胶水代码、调度、工程细节上，离业务越来越远。
- **意图生成工具（Copilot Studio / Coze 一类）**：你给一句"目标"，它回一段提示词。简单任务够用，过程不可控、沉淀不下来，复杂业务接不住。

**Unigen 是第三条路。** 你不写代码，也不只描述目标——你写**过程**：第一步做什么，第二步做什么，遇到 X 调用哪个工具，什么条件转人工。Unigen 把这份指南连同工具、子 Agent、存储配置，编译成一个**完整的 Agent 系统**（多份带 front-matter 的文件），而不是一段孤立的提示词。

换个分工，换一份指南：客服、文案、审核、调度器，共享同一套执行底座，差别只在指南。

## 为什么弱模型也能跑

还是苏东坡。

强模型是见多识广的苏东坡，弱模型是没怎么出过门的苏东坡。给没出过门的苏东坡写电商指南，道理不变，只是你得多替他写几笔：他没见过的环节，你不能省，得用他懂的词，一句一句铺到位。

落到模型上：

- **指南要覆盖模型推理不到的地方。** 模型会的那步，一句带过；模型没把握的那步，写明白。弱模型推理不到的多，你就写得密一些。
- **词汇要对齐它的世界。** 只要模型的自然语言理解（指代消解这类）过关，你总能找到它听得懂的措辞，把没把握的步骤讲到它能照做。反过来，你对它说"开机""登录后台"——就像对苏东坡说电脑——词超出了它的经验，指南再细也无效。
- **粒度是个旋钮。** 模型强，会得多，指南写粗，甚至一句话交给它自己拆；模型弱，会得少，把节点切细、约束写死。靠这一个旋钮，同一套底座从前沿大模型适配到本地小模型。

> 一句话：别人赌模型够聪明，Unigen 让你把没把握的地方写进指南。

## 怎么写一个 Agent

一个 Agent = **front-matter（能用什么）+ 指南正文（怎么用）**。
两部分都在图形界面里编辑：勾选工具、拖拽子 Agent、富文本写正文。下面展示的是界面无感、由 Unigen 在底层替你生成的真实文件。

### 例 1 · 通用 Agent（自带三路发现）

```markdown
---
name: agent
description: General-purpose agent. Every planned node issues a three-path discovery batch (tools/skills/knowledge) before execution. Discovery is prerequisite; degradation only on exhaustion. Clarification nodes follow the same rule.
maxSteps: 1000
tools:
  - { type: builtin, id: "builtin::search_tools",  alias: search_tools }
  - { type: builtin, id: "builtin::invoke_tool",   alias: invoke_tool }
  - { type: builtin, id: "builtin::search_skills", alias: search_skills }
  - { type: builtin, id: "builtin::内部工具",    alias: 内部工具 }
  - { type: builtin, id: "builtin::query_all_knowledge", alias: query_all_knowledge }
---

# IDENTITY

你是一个通用 Agent。你的能力来自：先把任务拆成节点图，再在每个节点执行前强制发起一次"三路发现"——查工具、查技能、查知识库。
不因节点看起来简单、不因"我自己大概能搞定"、不因"工具已经够用"而跳过任何一路。
```

`tools` 里每一项就是一个工具声明：`type` 表明来源（`builtin` 内置 / `mcp` 外部服务 / `skill` 技能 / `agent` 子 Agent），`alias` 是指南正文里调用它时用的名字。

### 例 2 · 多 Agent 编排 + 结构化输入

```markdown
---
name: ecom-visual
description: 电商视觉内容生产协调者。调度调研定位、风格、分镜、交付四个子 Agent，按阶段接力产出成品。
tools:
  - { type: agent, path: ./steps/briefing-and-positioning.md }
  - { type: agent, path: ./steps/style-direction.md }
  - { type: agent, path: ./steps/shot-design.md }
  - { type: agent, path: ./steps/delivery.md }
---

# 电商视觉设计调度官

你负责把客户给的设计资料转化为可落地的电商视觉成品。从信息提炼到市场定位，再到风格确定、出图规格、最终交付，每一步都有专门的执行人。

## 全局约束

以下规则贯穿全程，任何步骤不得违反：

...

## 阶段 A：信息提炼与定位

调用 briefing-and-positioning 消费原始设计资料，产出核心卖点、slogan、目标市场、参考案例。这是后续所有决策的基础。

## 阶段 B：风格确定

调用 style-direction，基于阶段 A 的产出，归纳目标人群主流风格、提取产品设计内涵、总结情绪价值，给出一个视觉风格令牌。这个令牌是后续出图规格的唯一风格依据。

## 阶段 C：出图规格

调用 shot-design，把风格令牌落到完整的画面规格：主体、材质、环境、光影、镜头、文字排版、色彩方案、画面质感、负面提示词。它产出的 `render_spec` 是一段可直接投喂文生图模型、一次性产出含文字成品的完整中文提示词。

## 阶段 D：交付

调用 delivery，消费 shot-design 的 `render_spec`，逐条核对全局约束，补齐产品文字信息与 Logo，输出最终成品及交付说明。任一约束不满足，退回对应阶段重做，不放行。
```

`type: agent` 的每一项指向一份子指南文件。调度官依次调用四个子 Agent，把上一步的产出作为下一步的输入——子 Agent 只负责自己那一段，接力完成整条流程。
### 子 Agent 之间怎么传数据

上面这份指南读起来像一份流程说明，没有变量，没有存储。子 Agent 之间的信息像函数调用一样逐层传递：调度官调用 briefing-and-positioning，拿回它的产出，再把产出交给 style-direction。上游的输出就是下游的输入，调用返回即完成交接。这是**堆栈式协作**——贴近自然语言，不留痕迹，多数流程用它就够。

需要让多个子 Agent、跨多个步骤反复读写同一份上下文时，可以使用共享存储。

### 例 3 · 接外部工具（MCP）

```markdown
---
name: url-summarizer
description: 网页内容提取与摘要。
tools:
  - { type: mcp, server: web, tool: fetch, alias: web_fetch }
  - { type: mcp, server: web, tool: parse, alias: html_parser }
---

你是网页内容提取专家。用户给 URL 后：

1. 用 web_fetch 获取页面
2. 用 html_parser 提取正文
3. 输出核心内容摘要（200 字以内）
```

## 项目与"发布为类型"

Unigen 以**项目**为工作单元，一个项目就是一个 Agent 的工作台（含会话管理）。

1. **新建项目**——从某个"指南类型"开始，或从空白开始。类型决定项目初始的角色、工具与协作结构。
2. **编辑指南**——在图形界面里调步骤、增减工具、绑定知识库、编排子 Agent。
3. **发布为类型**——把改好的指南发布成一个新的"类型"，之后所有新项目都能从这个类型起步。

```
project/
├── meta/
    ├──  pac/     # 当前 Agent 的工作指南（GUI 维护）
```

好的指南沉淀下来，能复用、能分享。用的人越多，类型库越厚，新项目冷启动越快。一份业务"画"成指南，下次换个人、换个场景直接接着用。

## 能力底座

| | 说明 |
|---|---|
| **兼容 MCP 与 Skill** | 已有的 MCP Server、Skill 直接接入，零改造。工具来源在 front-matter 里以 `type` 区分。 |
| **私有知识库** | 每个 Agent 可挂载私有数据与专有知识。通过 `query_all_knowledge` 检索、通过专用工具写入。执行节点前先取相关上下文，用偏好和约束收敛决策，不靠事后纠错。 |
| **多种存储通信** | KV（结构化数据）、向量（语义检索）、模板变量（正文里直接引用存储内容，省 token）。多 Agent 通过它们协作。 |

## 适合谁

| 角色 | 你的重复工作 | 用 Unigen 做什么 |
|------|------|------|
| 内容创作者 | 日报、周报、素材整理 | 写一次流程，AI 执行，你只审核 |
| 运营 / 客服 | 标准应答与分流 | 写一份 SOP，发布成类型，持续运行 |
| 数据分析师 | 固定分析步骤 | 声明数据源工具 + 分析流程 |
| 开发者 | 快速搭多 Agent 系统 | 不写代码，组合 MCP / Skill / 子 Agent |

**适合的范围**：从单轮问答（一份简短指南即可）到多步骤长链条任务（拆成子 Agent 接力），只要过程说得清，就覆盖。
**不适合**：每次都要全新创造性思考的任务。能固化的是过程和范式；没有固定过程可固化的，属于另一类问题。

## 快速开始

从Release下载对应版本，开始执行。

或者从源码编译:

```bash
git clone https://github.com/masol/unigen
cd unigen
npm i && npm run start
```

打开后三步：**新建项目 → 在 GUI 里写指南 → 运行**。改满意了，发布成类型。

## 常见问题

**要会写代码或懂 YAML 吗？**
不需要。图形界面覆盖常用配置。底层那份 front-matter 文件对想直接编辑的高级用户开放，但不是必须。

**弱模型也能用吗？**
能，这是设计目标之一。模型弱，说明它推理不到的地方多，你把节点切细、约束写死，用它能懂的词把每步讲到它照做即可。详见上文「为什么弱模型也能跑」。

**和 LangChain 什么关系？**
LangChain 用 Python 编排 Agent，Unigen 用自然语言指南 + 图形界面。能做的事有重叠，面向的人不同。

**和 Copilot Studio 什么区别？**
它从"目标"生成一段提示词；Unigen 要你把面向人的"工作过程"写清楚，产出带工具、子 Agent、存储配置的完整 Agent 系统，过程可控、可复用。

**Agent执行错了怎么办？**
看执行日志，定位到哪一步，在界面里改那一步的描述即可。

**支持哪些模型？**
主流 LLM 均可（OpenAI / Claude / 本地模型），按模型能力调整指南粒度，详见配置文档。

## 为什么叫"编译器"——原理在 Wiki

Unigen 把自然语言指南"编译"成可执行的 Agent，是因为它把 LLM 看作早期的裸机编程：自然语言是界面，训练得到的权重是出厂预置的指令库，你在推理期改不动它。你用自然语言重新定义流程，相当于绕开改不动的权重，在外面给它补一段它没把握的过程——一次轻量的"二次训练"。多工作流与神经网络在数学上都是复合函数的复合，工作指南偏重逻辑，因此可解释。也正因为每个 Agent 用 front-matter 自维护工作流，Unigen 才有望从"写指南得 Agent"长成一个超长链条代码生成与执行平台。
